# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Keep this file current as you work.** Whenever a change adds or alters a build-time convention future work would need to know about — a new signal-based generator in `pelicanconf.py`, a new `PLUGINS`/`STATIC_PATHS`/`EXTRA_PATH_METADATA` entry, a new dependency, a new template/partial wiring pattern — update the relevant section here (or add one) in the same change, not as a separate follow-up. Don't wait to be asked.

## What this is

A [Pelican](https://getpelican.com) (Python static site generator) project for **datacloudhero.com**. Content is written in Markdown, rendered through a custom theme (`themes/mytheme`), and the built `output/` is deployed as a static site.

The site has two independent parts that never share templates:
- **Site root** (`/`, `/fr/`, `/de/`, `/es/`) — a Pelican `Page` rendered through its own standalone template (`landing.html`), hand-authored, entirely separate from the blog theme (see below).
- **`/blog/`, `/fr/blog/`, `/de/blog/`, `/es/blog/`** — everything else Pelican generates (articles, tags, categories, authors, search index) via `themes/mytheme`.

The site is multi-language (EN default, FR/DE/ES) via Pelican's *native* translation mechanism, not the `i18n_subsites` plugin - see "Multi-language content" below before touching anything language-related.

## Commands

```bash
pip install -r requirements.txt      # pelican, markdown, pelican-sitemap — the only real deps
npm ci                               # tailwindcss CLI + @tailwindcss/typography — the blog theme's only JS/CSS build deps

make html        # rebuilds theme/css/style.css (see below), then one-off Pelican build -> output/
make devserver   # build + watch + serve at http://localhost:8000 (edit-reload loop)
make serve       # serve an already-built output/ without regenerating
make publish     # production build with publishconf.py -> output/ (absolute URLs, feeds on)
make clean       # rm -rf output/

# equivalent raw commands (what devserver/publish wrap):
pelican content -o output -s pelicanconf.py    # dev config, SITEURL=""
pelican content -o output -s publishconf.py    # prod config, SITEURL="https://datacloudhero.com"
```

There is no lint/test suite in this repo. `DELETE_OUTPUT_DIRECTORY = True`, so `output/` is wiped and fully regenerated on every build — never hand-edit files under `output/`, they don't survive the next build.

**CSS build**: `themes/mytheme/static/css/style.css` (the blog theme's stylesheet) is a **generated file** — a Tailwind CLI build output, not hand-edited directly. Its source is `themes/mytheme/static/css/tailwind-input.css` (`@tailwind` directives + the site's design tokens/custom component classes in `@layer base`/`@layer components`), compiled via `tailwind.config.js` (`content` globs over `themes/mytheme/templates/**/*.html`, `darkMode: 'class'`) and `npm run build:css` (`npm run watch:css` for a live-rebuild loop). Every `make` target that touches `output/` depends on a `css` target that runs this automatically — but `make devserver`'s own watch/reload loop does **not** know about `tailwind-input.css` or template class changes, so for a CSS edit-reload loop run `npm run watch:css` in a second terminal alongside `make devserver`. `style.css` is still committed to git (not gitignored) since nothing guarantees a build step runs before deploy otherwise — see CI below. `pygments.css` (syntax highlighting) is hand-written CSS, not run through Tailwind. `package.json`/`tailwind.config.js` exist at the repo root purely for this one CSS build step — there's no other JS runtime/framework/bundler in this otherwise pure-Python project, so `node_modules/` is gitignored and nothing under it is depended on beyond the `tailwindcss` CLI binary.

**Cache-busting**: the site is proxied through Cloudflare, which caches `theme/css/style.css`/`pygments.css` at the edge for hours regardless of whether the file actually changed (observed `max-age=14400`) — since both are always requested at the same URL, a CSS-only deploy could stay invisible to already-cached visitors for up to 4 hours. `ASSET_HASH` (`pelicanconf.py`, right after `THEME`) hashes both files' actual content on every Pelican run and `base.html` appends it as a `?v=<hash>` query string on each `<link>` — a real content change gets a new cache key automatically, an unrelated deploy keeps the same hash and stays cached. This only covers the two theme stylesheets; if another cache-busted asset is ever needed, extend `ASSET_HASH` rather than inventing a second mechanism.

Deployment is automatic: `.github/workflows/gh-pages.yml` installs Node + runs `npm ci && npm run build:css` (so `style.css` is fresh even if a commit forgot to rebuild it locally), then `pelican content -o output -s publishconf.py` on every push to `main`/`master`, publishing `output/` to GitHub Pages. `make github` (local `ghp-import` to a `gh-pages` branch) is an older/alternate path defined in the Makefile but not what CI uses.

## Architecture

### URL scheme is centralized in `pelicanconf.py`

Every content type is deliberately routed under `blog/...` (`ARTICLE_URL`, `ARTICLE_SAVE_AS`, `TAG_URL`, `CATEGORY_URL`, `AUTHOR_URL`, `INDEX_SAVE_AS`, etc. are all overridden away from Pelican's defaults). The site root path is reserved for the static landing page. When adding any new content type/URL, follow this `blog/{...}` convention rather than Pelican's defaults.

### The landing page is a real Page, but with its own document shell

The landing page is a real Pelican `Page` (`content/pages/landing.html` + `themes/mytheme/templates/landing.html`), but it deliberately does **not** extend `themes/mytheme/templates/base.html` — it has an entirely different visual identity (dark-only hero, Google Fonts, DaisyUI components) from the blog theme, so it carries its own full `<head>`/`<body>` shell instead. Both halves of the site run on Tailwind CSS, but as two independently-configured setups that never render on the same page: the landing page loads Tailwind's Play CDN script plus DaisyUI (`cdn.tailwindcss.com` + `daisyui` CDN CSS, zero build step, dark-only, no `dark:` variants anywhere), while the blog theme is a real Tailwind CLI build with its own design tokens and a light/dark toggle (see "Commands" above and `static/css/style.css` below) — don't assume "both are Tailwind" means they can share templates, markup conventions, or class vocabulary; the "never share templates" rule and the `HTMLReader` reasoning below are unaffected by either side's CSS framework.

The split, and why it's shaped this way: Pelican's built-in `HTMLReader` (used for `.html` content files) only extracts `<title>` and `<meta name="...">` from `<head>`, and everything between `<body>`/`</body>` — it silently drops everything else in `<head>` (so raw `<style>` blocks, CDN `<script src>` tags, font links can't live in the content file) and it discards attributes on the `<body>` tag itself (so anything that has to be on `<body>`, like Alpine's root `x-data`/`x-init` scope, can't live in the content file either). Given that:
- `themes/mytheme/templates/landing.html` holds the whole document shell: `<head>` (Tailwind CDN, Alpine.js, Google Fonts, the custom `<style>` blocks, OG/Twitter meta), the `<body class="grid-bg" x-data="{...}" x-init="...">` opening tag (this is where the page's Alpine root scope - menu state, contact form, reveal-on-scroll - lives), then `{{ page.content|safe }}`, then the trailing footer `<script>` tags before `</body></html>`.
- `content/pages/landing.html` holds just what used to be *inside* `<body>` (nav, hero, services, stack, process, contact modal, FAQ), plus a small metadata `<head>` using Pelican's HTML-page convention (`<meta name="save_as" content="index.html">`, `<meta name="url" content="">`, `<meta name="template" content="landing">`) to route it to `output/index.html` via the `landing` template instead of the blog's default `PAGE_URL`/`PAGE_SAVE_AS` pattern.

`ARTICLE_EXCLUDES` includes `'pages'` for a non-obvious reason: `ARTICLE_PATHS` defaults to `[""]`, so Pelican's `ArticlesGenerator` walks *all* of `content/`, including `content/pages/` — without the exclude, `landing.html` gets picked up as both an Article and a Page and they race to write `output/index.html`.

Because the landing template is standalone, asset paths inside it are easy to get wrong: theme static files (logo, favicon, social-card) live under `theme/img/...` in the built output (see below), not `img/...` — a past bug was the landing page linking to the wrong prefix.

Two more root-level files ride along via `STATIC_PATHS`/`EXTRA_PATH_METADATA` (unrelated to the Page above — these are still verbatim-copied static files, not Pelican content):
- `content/extra/favicon.ico` — a duplicate of `themes/mytheme/static/img/favicon.ico`, kept only so `/favicon.ico` exists at the domain root (browsers fall back to fetching that path for tabs with no `<link rel="icon">` to read, e.g. the raw-text `blog/{slug}.md` mirrors below).
- `content/extra/index.md` — a **hand-written** Markdown summary of the landing page (services, stack, process, contact), linked from `llms.txt`. It is *not* auto-derived from `content/pages/landing.html`: that page has no clean text to extract (nav/tech-stack markup is legitimately duplicated for responsive/marquee reasons, the contact email is Cloudflare-obfuscated in the source, and the FAQ copy only exists inside an Alpine `x-for="... in [...]"` JS array, invisible to any HTML→text pass). Update it by hand when the pitch changes materially.

The landing page's contact `mailto:` (and the blog's `CTA_BUTTON_LINK`/`CTA_FOOTNOTE` in `pelicanconf.py`) is `info@datacloudhero.com`. Note Cloudflare's Email Address Obfuscation rewrites any plain `mailto:` into a `data-cfemail="..."` blob at the edge on every response — seeing that in a live `curl`/view-source is expected, not a sign the address reverted; decode it (XOR each byte with the first byte) to check what it actually points at.

### Theme structure (`themes/mytheme/`)

- `templates/base.html` — full HTML shell (nav, search widget, theme toggle, footer, global `<script>` blocks) used by every Pelican-rendered page. The mobile nav toggle and the language-switch/AI-actions dropdowns (`partials/ai_actions.html`) are plain Alpine.js (`x-data="{ open: false }"`, `@click`, `x-show`/`x-cloak`, `@click.away`) rather than any Bootstrap-style JS component — Alpine is already loaded here for the theme toggle/search/contact-modal, so new interactive chrome should follow the same pattern rather than introducing another one.
- `templates/blog_base.html` — extends `base.html`, adds the year-grouped sidebar of all posts; everything under `/blog/` extends this, not `base.html` directly.
- `templates/article.html`, `page.html`, `category.html`, `tag.html`, `author.html`, `authors.html`, `archives.html`, `index.html`, `404.html` — extend `blog_base.html`.
- `templates/partials/` — small includes pulled into article pages: `author_card.html`, `cta.html` (driven by the `CTA_*` settings in `pelicanconf.py`), `ai_actions.html` (see below).
- `templates/search.html` — a `DIRECT_TEMPLATES` entry; the site has no server-side search, it's Alpine-less vanilla JS (in `base.html`) that fetches `blog/search-index.json` (generated via `SEARCH_SAVE_AS`/`SEARCH_URL`) and filters client-side.
- `static/img/` — `favicon.ico`, `logo.svg`, `social-card.png`. Pelican copies this whole tree to `output/theme/...`, so **any reference to these assets — including from the standalone landing page — must use the `theme/img/...` prefix**, not `img/...`.
- `static/css/style.css` — a Tailwind CLI build output (see "Commands" above), **not hand-edited directly** — edit `static/css/tailwind-input.css` and rebuild. Dark mode is Tailwind's `darkMode: 'class'` strategy: a `.dark` class on `<html>`, toggled by `#themeToggle`'s click handler and set pre-paint by an inline FOUC-guard script in `base.html`, both reading/writing `localStorage['theme']`. Six self-owned design tokens (`--color-body`, `--color-body-bg`, `--color-border`, `--color-tertiary-bg`, `--color-secondary`, `--color-emphasis`, defined once in `tailwind-input.css`'s `@layer base` for light and again under `.dark` for dark) plus `--accent`/`--accent-hover`/`--accent-rgb` are what every themed color in the site derives from — there's no framework supplying these automatically, so a new component needs to be built on these vars (or Tailwind's own `dark:` variant, backed by the same `darkMode: 'class'` toggle) rather than assuming a default palette. `tailwind-input.css`'s `@layer components` holds every component-specific class (`.sidebar-*`, `.author-*`, `.search-*`, `.tag-pill`, `.cta-box`, `.container`, `.btn`/`.btn-outline`/`.btn-dark`, `.form-control`, `.dropdown-menu`/`.dropdown-item`, `.contact-modal-*`, `.btn-glow`, ...) — prefer adding to this named-class system over inlining long Tailwind utility strings for anything reused across templates, matching the existing pattern. `partials/ai_actions.html` is included from `article.html`, driven by `.ai-actions`/`.dropdown-*` here.

The one exception to "no plugins" is `@tailwindcss/typography` (`tailwind.config.js`), which styles raw markdown-rendered HTML that has no classes of its own to hook utilities onto — `article.html`'s `.article-body` and `page.html`'s `.content-wrap` carry `prose prose-lg max-w-none` to activate it (`max-w-none` cancels the plugin's own 65ch cap, since `.content-wrap` already constrains width to 780px). It's deliberately *not* applied to `blog_base.html`'s shared `.content-wrap`/category/tag/author/archives/index pages - those are hand-authored template markup with their own component classes already, not raw content, and typography's descendant selectors (link/image/code styling) would fight components like `.tag-pill`/`.btn` if applied that broadly. `.prose`'s color variables (`tailwind-input.css`, right where the plugin is invoked) point at the same `--color-*`/`--accent` tokens everything else uses, rather than the plugin's own gray scale - no separate `prose-invert`/dark handling needed, since those tokens already flip under `.dark` on their own. Fenced code blocks are Pygments/`pygments.css` output (`.highlight > pre > code`), which already fully styles the box in both themes - a `.prose.article-body .highlight *` override neutralizes the plugin's own `pre`/`code` chrome there specifically, so the two don't stack.

### Content authoring

Markdown files live in `content/blog/` (flat, not `content/blog/articles/`) — this is just a source-tree organization convention for grouping articles apart from `content/pages/`/`content/extra/`; it has no effect on output URLs, which are entirely driven by `ARTICLE_URL`/`ARTICLE_SAVE_AS` etc. in `pelicanconf.py` regardless of where the source file lives (`ARTICLE_PATHS` is unset, so Pelican's `ArticlesGenerator` still walks all of `content/` except `ARTICLE_EXCLUDES`). Metadata is the classic Pelican `Key: value` header block terminated by a blank line (`Title`, `Date`, `Category`, `Author`, `Tags`, `Summary`). `AUTHORS_INFO` in `pelicanconf.py` maps author names to avatar/title/social links used by `author_card.html` — a new author must be added there, not just in the article's `Author:` field, or the card renders without the extra info.

### Multi-language content (EN default, FR/DE/ES)

Translations use Pelican's *built-in* mechanism - `Lang:`/`lang` metadata plus a `Slug:`/`slug` that matches the English original - **not** the `i18n_subsites` plugin. `i18n_subsites` runs a full nested `Pelican(...).run()` per language inside the main build, which would make every custom generator below (and the `pelican-sitemap` plugin) fire once per language and need "am I the main build or a subsite" guards everywhere (`output/fr/robots.txt`, `output/de/sitemap.xml`, ...). Plain translations keep everything to one build, one shared context, one `sitemap.xml`.

**The catch to know about**: `ARTICLE_TRANSLATION_ID`/`PAGE_TRANSLATION_ID` default to `'slug'`, and Pelican's `process_translations()` puts only *one* canonical item per slug group (the `DEFAULT_LANG` one, when present) into the `articles`/`pages` context Jinja templates normally see - every other-language version of that same slug is filtered into a separate `article_generator.translations` list that **templates don't get by default**. `_expose_translations_to_context` (in `pelicanconf.py`) copies it into the shared context dict so templates can do `articles + translations` (see `blog_base.html`'s sidebar). `_write_markdown_mirrors` was updated the same way - iterate `articles + translations`, not just `articles`, or non-English `.md` mirrors silently never get written.

- **Articles**: `content/blog/fr/`, `content/blog/de/`, `content/blog/es/` (parallel to the flat English ones in `content/blog/`) - same `Slug:` as the English original, `Lang: fr`/`de`/`es`. URLs come from `ARTICLE_LANG_URL`/`ARTICLE_LANG_SAVE_AS` = `{lang}/blog/{slug}/` (set in `pelicanconf.py`, right after the English `ARTICLE_URL`/`ARTICLE_SAVE_AS`) - unrelated to the source directory name, which is purely organizational. **An article with `{attach}`ed images** needs its own folder named `content/blog/YYYY-MM-DD-slug/` (the slug suffix matters - a bare `YYYY-MM-DD/` collides the day a second article publishes on the same date), containing one `{lang}/` subfolder per language it's translated into (`en/`, `fr/`, `de/`, `es/`, ...), each with its own copy of the image files under the same unsuffixed names - see `content/blog/2026-09-14-agent-memory-framework/` for the pattern. Pelican's `{attach}` only resolves a static file that lives in the same directory as the article referencing it, and only ever attaches one file to one output location, so translations sharing an image file by filename (even across different directories) trigger a Pelican warning ("output location already overridden") and silently wrong image URLs on the 2nd+ article. This also means a translated image usually needs re-authoring (not just relabeling the article) if the image itself has embedded text - the diagrams there were generated per-language from a small script, not hand-drawn (`content/blog/2026-09-14-agent-memory-framework/diagram-scripts/`: `build.py` renders each language's box labels + the shared `brand_mark.py` datacloudhero.com watermark into a `*.svg` per language/diagram, `render.py` rasterizes those to the `*.png` files the article actually references via `{attach}` - both scripts resolve their paths relative to their own location, run with `python3 build.py && python3 render.py` from that folder; `render.py` needs Playwright, which isn't one of the site's own `requirements.txt` deps, it's a one-off authoring tool. The two undated `*.svg` files one level up, in the article root, are the original Russian-labelled, differently-branded template this was built from - kept for reference, not read by either script). See also `content/blog/2026-09-15-gtm-engineer-role/` for a second instance of this same pattern.

**Recurring operation: swapping a third-party logo/watermark for the real brand mark in a supplied diagram.** Source diagrams handed over for an article (e.g. inside a zipped article draft) sometimes carry another vendor's credit mark baked into the SVG (a past example: a "LakedApp" wordmark+icon in the bottom corner) instead of datacloudhero.com's own. Fix this the same way every time, don't hand-draw a replacement: (1) keep the original supplied SVG unmodified as the article-root reference template (`content/blog/YYYY-MM-DD-slug/<diagram-name>.svg`, one level above `diagram-scripts/`), matching the existing "original template" convention above; (2) copy `brand_mark.py` from an existing article's `diagram-scripts/` verbatim - it's the reusable, article-independent generator for the real logo.svg vector artwork, nothing in it needs to change; (3) write a `build.py` for the new diagram that reproduces the original's layout/labels (translated per language) but calls `brand_mark(cx, cy, height)` where the third-party mark used to sit, instead of copying that mark's markup; (4) write a `render.py` that rasterizes each language's SVG to the PNG the article's `{attach}` reference actually uses, at 2x the SVG's native viewBox size like every other diagram in the site. Never keep, translate, or resize the third-party mark - always replace it outright with `brand_mark()`.

**Standard brand-mark size in diagrams**: every `brand_mark(cx, cy, height=...)` call across every article's `diagram-scripts/build.py` uses `height=12` (SVG units) - small enough to read as a watermark/credit rather than compete with the diagram's own content. This was tuned down from an initial `17`/`15` after visual review; keep new diagrams consistent with it rather than picking a one-off size, and if it ever changes again, update it in every existing `build.py` (not just the new one) and re-run `build.py && render.py` in each article's `diagram-scripts/` to regenerate the SVGs/PNGs.
- **Landing page**: `content/pages/landing-fr.html`/`landing-de.html`/`landing-es.html`, same `landing.html` template as English, each with its own `<meta name="save_as"/"url">` (`fr/index.html`/`fr/`, etc.) and `<meta name="slug" content="landing">` matching the English version's slug so they link as translations. These are **hand-translated full copies**, not derived from the English file - same tradeoff as `content/extra/index.md`, see above. The language switcher (`EN / FR / DE / ES` links) is hardcoded per-language directly in each of the four content files (content bodies aren't run through Jinja, so it can't be templated) - if the switcher markup changes, update it in all four.
- **A regular blog `Page`** (e.g. Cookie Policy): unlike the landing page, this doesn't need a per-file URL override. `PAGE_LANG_URL`/`PAGE_LANG_SAVE_AS = '{lang}/blog/{slug}/'` (`pelicanconf.py`, right after the article equivalents) mirror `ARTICLE_LANG_URL`/`SAVE_AS` - Pelican's `Content.get_url_setting()` automatically looks for `PAGE_LANG_URL`/`SAVE_AS` whenever `page.lang != DEFAULT_LANG`, so a translation just needs `Lang: fr`/`de`/`es` + the same `Slug:` as the English original (e.g. `content/pages/cookie-policy-fr.md`, `Slug: cookie-policy`) and it's automatically routed and linked as a translation - no metadata overrides needed. This only kicks in when a Page has no explicit `save_as`/`url` override, so it doesn't affect the landing page translations above. The header/footer language switcher in `base.html` deep-links to `page.translations` the same way it already did for `article.translations`.
- **`/{lang}/blog/` index**: Pelican's own `IndexesGenerator` only ever builds *one* `/blog/` index (for `DEFAULT_LANG`) - there's no `INDEX_LANG_SAVE_AS` equivalent. `_write_lang_blog_indexes` (`pelicanconf.py`) hand-renders one per other language from a dedicated `blog_index_lang.html` template (no pagination - not enough content per language yet to need it), and manually fires `content_written` so `pelican-sitemap` picks each one up, the same trick used for the landing page before it became a real `Page`.
- **Theme chrome** (nav/footer/buttons/"Tags:"/"min read"/etc., i.e. *not* content): `UI_STRINGS` and `CTA_STRINGS` dicts in `pelicanconf.py`, exposed to Jinja via `JINJA_GLOBALS`. `base.html` resolves `current_lang` once (an explicit `current_lang` in context, e.g. from `_write_lang_blog_indexes`, wins; otherwise falls back to `article.lang`/`page.lang`/`DEFAULT_LANG`) and sets `t = UI_STRINGS[current_lang]`; templates use `{{ t.some_key }}` rather than hardcoded English. Adding a language means: add it to `LANGUAGES`, add a `UI_STRINGS[xx]`/`CTA_STRINGS[xx]` bundle (keep keys in sync across languages), write the content.
- **Known v1 scope boundary**: tags/categories/archives/authors listing pages stay unified/English-only (routes are not `_LANG_`-suffixed for these) - a French article still links to an (English-routed) tag page. `llms.txt` also stays English-only. Widening either is a repeat of the `_write_lang_blog_indexes` pattern, not done yet.

### Generated machine-readable mirrors (`pelicanconf.py`, bottom half)

Five custom generators are wired up via `pelican.signals.article_generator_finalized` directly inside `pelicanconf.py` (no separate plugin package/folder for these — they're plain functions + `_signals.connect(...)` calls at module scope):

- `_write_markdown_mirrors` — for every article `blog/{slug}/index.html` (or `{lang}/blog/{slug}/index.html`), also writes a sibling `.md` containing the raw Markdown body (metadata block stripped) plus a short source/date header. This is what the "Copy page as Markdown" article button, `llms.txt`, and the ChatGPT/Claude/Perplexity links in `ai_actions.html` all point at.
- `_write_llms_txt` — writes `output/llms.txt` at the site root, following the [llmstxt.org](https://llmstxt.org) format: `# title` / `> summary`, a `## Site` section linking `content/extra/index.md`, then a `## Blog` section with `- [title](md_url): desc` for every (English) article.
- `_write_robots_txt` — writes a minimal `output/robots.txt` (`Disallow:` = allow everything) pointing `Sitemap:` at `sitemap.xml`. The domain is proxied through Cloudflare, which was observed serving its own "Content Signals" boilerplate text at that path *only as a fallback* when origin had no `robots.txt` at all — once this file exists, Cloudflare passes it through untouched.
- `_expose_translations_to_context` / `_write_lang_blog_indexes` — see "Multi-language content" above.

`sitemap.xml` itself comes from the real 3rd-party `pelican-sitemap` plugin, pinned via `PLUGINS = ['sitemap']` and `SITEMAP = {...}` (both in `pelicanconf.py`) rather than left to Pelican's auto-discovery — leaving `PLUGINS` unset makes Pelican auto-load *any* installed `pelican.plugins.*` package, which previously caused `sitemap.xml` to appear in local dev (because `pelican-sitemap` happened to be pip-installed there) while being silently absent from the real CI build (`requirements.txt` didn't have it). Pin new plugins in both `PLUGINS` and `requirements.txt` together, never rely on auto-discovery. It picks up `hreflang` alternates for free from Pelican's own `article.translations`/`page.translations` - no extra work needed there.

All five run automatically on every build (dev and publish) — no extra command needed. If article URL/save-as conventions in `pelicanconf.py` change, the `_os.path.dirname(article.save_as) + '.md'` path derivation used by more than one of these functions needs to change with them.

### `ai_actions.html` partial

Renders a per-article dropdown ("Copy page as Markdown" / "View as Markdown" / "Open in ChatGPT" / "Open in Claude" / "Open in Perplexity"), included from `article.html`. The clipboard-copy behavior is a delegated click handler in `base.html` (`.js-copy-markdown`), not in the partial itself — keep the two in sync if either is renamed. The ChatGPT/Claude/Perplexity links only pre-fill a prompt referencing the article's `.md` URL; they don't guarantee the target service fetches it (depends on that service's browsing being enabled).

### Contact form

Name/email/message + a hidden honeypot field + Cloudflare Turnstile, POSTing to `/api/contact` (infrastructure outside this repo - not a Pelican-generated route, presumably a Cloudflare-side handler in front of GitHub Pages; nothing here to configure beyond the sitekey below). The submission behavior - state, the POST itself, success/error handling, resetting Turnstile - is one shared Alpine.js component, `contactForm(successMessage, errorMessage)` in `themes/mytheme/static/js/contact-form.js`, used by both halves of the site with framework-native markup on each side. Both halves are Tailwind now (see the landing-page split above), but stay on two separate, independently-configured setups (blog: CLI build + own `--color-*` tokens; landing: Play CDN + DaisyUI) that never render on the same page, so there's no risk of the two class vocabularies colliding - just no reason to assume a class means the same thing on both sides.

On a successful submit, the modal swaps the form out for a plain confirmation view instead of leaving the now-cleared form visible underneath a success message (`submitted` state, toggled via a `<template x-if="!submitted">`/`x-if="submitted"` pair around the `<form>`/success `<div>` in each modal - `x-if` fully unmounts the form rather than just hiding it, so its cleared fields/honeypot/Turnstile widget aren't lurking underneath), then auto-closes ~2.5s later (`autoCloseTimer` in `contact-form.js`). Every "open" trigger calls `openContactForm()` (not `showContactForm = true` directly) - it cancels any still-pending auto-close timer and resets `submitted`/`status`/`error` before showing, so a visitor who closes early and reopens for a new message always gets a clean form, and a timer from an old submission can't fire and yank the modal shut mid-typing. A new open trigger (there isn't one today beyond the two existing CTA buttons) must call `openContactForm()` too, not set `showContactForm` directly, or it'll skip that reset.

- **Landing page**: each `content/pages/landing*.html` wraps its own CTA section + modal in `<div x-data="contactForm('<success message>', '<error message>')">` with its *own* hardcoded translated success/error strings (content bodies aren't run through Jinja, so `UI_STRINGS` isn't reachable there - same constraint as the language switcher). Before this, `submitContact()` lived inline in the shared `landing.html` *template*'s `<body x-data="{...}">`, which is why every language actually showed the same English success/error text regardless of `Lang:` - moving to per-file arguments fixed that as a side effect.
- **Blog**: `partials/cta.html` wraps the existing CTA box in `x-data='contactForm({{ t.contact_success|tojson }}, {{ t.contact_error|tojson }})'` (**single-quoted** - `|tojson` always emits double-quoted JS string literals, which terminate a double-quoted HTML attribute at the first embedded quote and truncate the Alpine expression mid-call) and includes `partials/contact_modal.html`, a Tailwind-native equivalent of the landing modal (its own `.contact-modal-card`/`.form-control` component classes in `tailwind-input.css`, visibility driven by Alpine's `x-show`/`x-cloak`/`@click.away`). Its copy comes from `UI_STRINGS` (`contact_eyebrow`/`contact_modal_title`/`contact_name`/`contact_email`/`contact_message`/`contact_send`/`contact_sending`/`contact_success`/`contact_error`) like the rest of the blog chrome - visually it deliberately echoes the landing page's own modal (dark rounded card, green eyebrow label, glowing `.btn-glow` submit button) but adapts to the blog's light/dark toggle instead of being fixed-dark like landing's. `.contact-modal-card` sets its own `background: var(--color-tertiary-bg)` directly (there's no Bootstrap `.bg-body-tertiary` utility to reach for anymore) - keep it on `--color-tertiary-bg`, not `--color-body-bg`, since in dark mode `--color-body-bg` and `.btn-dark`'s fixed near-black land close enough together that a `.btn-dark` submit button on a `--color-body-bg` panel would nearly disappear.
- Both `landing.html` and `base.html` load `theme/js/contact-form.js` **before** the Alpine CDN script tag - it defines the global `contactForm()` function Alpine looks up while scanning the DOM for `x-data="contactForm(...)"`, so it has to already exist by the time Alpine's own (also deferred) script runs its init pass.
- The Turnstile sitekey (`0x4AAAAAAEM7muzBPUFiEYFd`) is hardcoded in both `content/pages/landing*.html` and `contact_modal.html` - update both if it ever rotates. Each `cf-turnstile` div also sets `data-language` explicitly (`contact_modal.html`: `{{ current_lang }}`; each `landing*.html`: its own hardcoded language code) - without it, Turnstile defaults to auto-detecting the visitor's browser/OS locale rather than matching the page's actual language, so a new language needs its own `data-language` value added in both places, the same way `UI_STRINGS`/`CTA_STRINGS` need a new bundle.

### Social-share previews (`og:image` etc.)

`base.html` (all Pelican-rendered pages) sets `og:*`/`twitter:*` meta tags itself — before this, the blog had none at all, so unfurlers (Telegram etc.) fell back to scraping the first `<img>` in the page HTML, which was the author avatar from `partials/author_card.html`. The image picked is: on an article page, the first `<img>` found in `article.content` via the `first_image` Jinja filter (`_first_image` in `pelicanconf.py`, a small regex over the rendered HTML, resolving a relative `src` against `SITEURL`); otherwise — article has no image, or it's a non-article page (`/blog/` index, tag/category/author/archives, a plain `Page` like Cookie Policy, 404, search) — the same `theme/img/social-card.png` the landing page uses (`landing.html` sets its own `og:image` independently, since it doesn't extend `base.html`). If article URL conventions or the markdown renderer's `<img>` output shape change, check `_first_image`'s regex still matches.
